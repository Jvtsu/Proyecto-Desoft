MEJORAS PROPUESTAS PARA pulsar_etapa3.ipynb
===========================================

1) ERRORES Y ROBUSTEZ DE CÓDIGO
-------------------------------

1.1 Robustez en parsing e impresión de glitches
- Validar siempre ausencia de claves opcionales (GLEP, GLF0, GLF1, GLF2) antes de formatear.
- Mantener salida segura cuando falten parámetros en el .par (sin romper ejecución).
- Registrar glitches incompletos en un warning explícito para trazabilidad.

1.2 Dependencia del estado del kernel
- Evitar variables implícitas heredadas entre celdas.
- Definir explícitamente variables clave usadas por gráficos/residuos (f0_teo, f1_teo) en el flujo principal.
- Garantizar ejecución lineal desde "Restart + Run All" sin errores.

1.3 Manejo de casos borde
- Si params['glitches'] está vacío, evitar acceso por índice [0] y [-1].
- Si el .dat tuviera líneas corruptas o columnas faltantes, reportar cantidad de filas descartadas.
- Verificar monotonicidad temporal en MJD y ordenar si fuera necesario.


2) CONSISTENCIA FÍSICA Y MODELADO
---------------------------------

2.1 Modelo de glitch actualmente simplificado
- El modelo implementa componente permanente:
  DeltaF0 = GLF0 + GLF1*dt + 0.5*GLF2*dt^2
  DeltaF1 = GLF1 + GLF2*dt
- Mejorable: incluir componente transiente de recuperación (decaimiento exponencial) cuando existan términos en el ephemeris:
  + sum_k( DeltaNu_dk * exp(-dt/tau_k) )
- Esto alinea mejor con literatura de glitches y recuperaciones post-glitch.

2.2 Rango de validez temporal del modelo de Taylor
- El notebook compara un .par ajustado en era NICER con datos RXTE bastante anteriores.
- Mejorable: explicitar que la extrapolación larga puede introducir sesgo sistemático incluso sin errores de implementación.
- Recomendación: ajustar por tramos temporales (segmentación interglitch) en lugar de extrapolación global larga.

2.3 Distinción glitch vs timing noise
- En fenómenos pequeños, la frontera entre glitch y timing noise no siempre es nítida.
- Mejorable: incluir cautela metodológica y, si se puede, un test/criterio de detección para separar ambos regímenes.

2.4 Métricas físicas adicionales
- Incluir braking index cuando haya derivadas temporales fiables:
  n = nu * nuddot / nudot^2
- Permite interpretar evolución de spin-down más allá de F0/F1.


3) ANÁLISIS CUANTITATIVO
------------------------

3.1 Métricas estadísticas faltantes
- Actualmente se reporta media y std de residuos.
- Mejorable: añadir chi-cuadrado reducido (chi2_red) para F0 y F1:
  chi2_red = sum((dato-modelo)^2/sigma^2) / dof
- Añadir RMSE y MAE para comparar variantes de modelo.

3.2 Comparación de modelos
- Implementar comparación explícita:
  (A) modelo base sin glitches
  (B) modelo con glitches permanentes
  (C) modelo con glitches permanentes + transientes (si aplica)
- Usar métricas comunes para justificar físicamente el mejor modelo.

3.3 Detección de eventos desde datos
- Mejorable: incorporar detector de cambios abruptos en F0/F1 (derivadas discretas robustas, umbral MAD/percentiles).
- Esto permite identificar glitches candidatos directamente desde el .dat.
